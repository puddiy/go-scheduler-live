Учебная пиксель-арт визуализация **настоящего** планировщика Go: горутины (G) — гоферы, слоты выполнения (P) — изометрические станции, OS-потоки (M) — тележки с номерами. Плюс сборщик мусора, выделенные объекты кучи, CPU-планирование, блокирующие сисколлы и stop-the-world паузы.

![Скриншот Go Scheduler Live](docs/screenshot-ru.png)

## Источник правды — реальный рантайм

Это **не симуляция**. Бэкенд запускает курируемые Go-нагрузки в подпроцессе под [`runtime/trace`](https://pkg.go.dev/runtime/trace), парсит бинарный трейс через [`golang.org/x/exp/trace`](https://pkg.go.dev/golang.org/x/exp/trace) и нормализует его в таймлайн, который фронтенд проигрывает по виртуальным часам. Каждое событие на экране — переходы состояний горутин, привязки P и M, циклы GC, суб-миллисекундные длительности STW, метрики кучи, причины блокировок — взято из настоящего трейса настоящей Go-программы, отработавшей на вашей машине секунды назад.

Состав очередей, отдельные кражи, runnext и жизненный цикл запаркованных M
неизвестны. Все Runnable показаны без назначения очереди. Панель **«Допущения»**
объясняет ограничения отрисовки, масштаб времени и опущенные детали. Первые
наблюдаемые состояния и частичные диапазоны не выдаются за реальные начала.
Подробности — в [аудите достоверности](docs/fidelity-audit.md).
Canvas и локальный контекст дизайна описаны в [настройке Superdesign](docs/superdesign.md).

## Возможности

- **Инспектор G/M/P** — клик по объекту или выбор с клавиатуры показывает наблюдаемое состояние, связи и последние нормализованные события trace. У M виден настоящий ThreadID; P до syscall отделён от текущего владельца. «Назад» и «Шаг» перемещают полный снимок по временным отметкам.

- **Шесть курируемых сценариев** — CPU-планирование, пинг-понг по каналам, давление на GC, блокирующие сисколлы (записанная передача P), горячий мьютекс, утечка горутин — каждый трейсится вживую с вашими `GOMAXPROCS` и числом горутин.
- **Настоящие OS-потоки (M).** Трейс несёт id исполняющего потока в каждом событии; тележки паркуются у P-станций и уходят вместе со своей горутиной в блокирующий syscall. Освобождение P и следующий владелец показаны отдельными событиями.
- **Настоящий GC.** GC-строка в масштабе прогона (полосы конкурентной разметки + STW-тики), heap-бар, покадрово окрашенный фазой GC, и STW-вспышка с честной длительностью паузы (микросекунды, а не растянутая анимация).
- **Журнал событий с причинностью** — все события трейса: кто кого разбудил, сколько ждала/бежала/была в syscall, переход syscall→Runnable и освобождение P без догадок о причине — строго из фактов трейса.
- **Зум и пан как на floor796** — колесо приближает до 6×, бирки id перерастеризуются и остаются чёткими.
- **Интерфейс RU/EN** — переключатель в шапке меняет весь UI, включая подписи и журнал.
- **Шарящиеся URL** — сценарий, параметры и момент паузы кодируются в адресную строку.
- **Статик-режим** — запечённая матрица трейсов деплоится на GitHub Pages вообще без бэкенда. У размещённого демо нет Go под капотом, поэтому его контролы выбирают ближайший запечённый прогон (GOMAXPROCS 1/4/8 на каждый сценарий), а не пишут новый трейс; страница об этом честно говорит, а локальный запуск пишет по-настоящему.

## Сценарии

| Сценарий | Чему учит |
|---|---|
| CPU-планирование | Выполнение G на разных P; отдельные кражи обычный trace не раскрывает |
| Каналы (ping-pong) | Кольцо горутин передаёт токены; большинство ждёт на `chan receive` |
| Давление на GC | Быстрые аллокации гонят циклы GC: конкурентная разметка + stop-the-world |
| Блокирующие сисколлы ¹ | Блокирующий read на M; записанное освобождение P и приобретение другим M |
| Горячий мьютекс | Один `sync.Mutex` сериализует N воркеров при любом числе P |
| Утечка горутин | Горутины вечно ждут канал без писателя; зона Ожидание только растёт |

¹ Только unix — нужен по-настоящему блокирующий `syscall.Read` на сыром fd. На Windows регистрируется пять сценариев вместо шести.

## Как устроено

```
cmd/workload (подпроцесс, runtime/trace в stdout)
      │  бинарный трейс
      ▼
internal/tracerun  ──►  internal/traceparse  ──►  internal/timeline   ──►  internal/api
  запуск → байты          x/exp/trace → события    доменная модель/DTO       HTTP/JSON
                                                                              │
                                                              web/ (Vite + TypeScript + PixiJS)
                                                    player/ (чистый stateAt(t) + вирт. часы)
                                                    scene/  (изометрический пиксель-мир, зум)
                                                    ui/     (DOM-хром, журнал, i18n)
```

- Трейс снимается в **отдельном подпроцессе** — горутины сервера в него не попадают, `GOMAXPROCS` задаётся на каждый прогон.
- Сценарии пейсят себя CPU-работой (`busyFor`), а не `time.Sleep` — сон паркует горутины и опустошает мир; канальные сценарии без пейсинга генерируют миллионы событий.
- Чистая логика (свёртка состояний, GC-сводка, раскладка, журнал причинности, математика вьюпорта, i18n) покрыта юнит-тестами; визуальный слой проверяют Playwright-харнессы, включая контракт контролов из 38 проверок.

Границы пакетов, правила привязки `mid`, таблица «что настоящее, а что реконструкция» и ловушки, сформировавшие дизайн, — в **[docs/architecture.md](docs/architecture.md)**.

## Быстрый старт

Требуется: **Go 1.25+**, **Node 22.12+ или 24+**.

```bash
# бэкенд (терминал 1)
go run ./cmd/server

# фронтенд (терминал 2)
cd web
npm install
npm run dev
```

Откройте http://localhost:5173. Новая комбинация параметров записывает trace; повтор воспроизводит кэш в памяти бэкенда.

Если `:8080` у вас занят, поднимите бэкенд на другом порту и укажите его дев-прокси: `go run ./cmd/server -addr :8085` вместе с `GMP_API_TARGET=http://localhost:8085 npm run dev`.

### Статическая сборка (без бэкенда)

```bash
go run ./cmd/bake                 # печёт web/public/runs/*.json
cd web
VITE_STATIC=1 npm run build       # фронтенд раздаёт запечённую матрицу
npx vite preview
```

Тот же конвейер деплоится на GitHub Pages при каждом пуше в `main` (`.github/workflows/pages.yml`).

## Тесты

```bash
go test ./...                     # инварианты планировщика (вкл. привязки M), анти-регрессии сценариев
cd web && npx vitest run          # чистая логика: state, GC, layout, причинность, share, viewport, i18n
node scripts/verify-controls.mjs  # Playwright: контракт контролов из 38 проверок (нужны оба сервера)
node scripts/verify-inspector.mjs # Playwright: выбор G/M/P, история, клавиатура и мобильная панель
```

> Бэкенд компилирует и запускает нагрузку по требованию (`go run`), поэтому ему нужны Go-тулчейн и исходники модуля в рантайме. Это локальный учебный инструмент — **не выставляйте dev-сервер наружу.**

## Заметки о честности

Авторитетный список — панель **«Допущения»**. Внутренности очередей и кражи
остаются неизвестны. Лимиты рисования не меняют счётчики G. GOMAXPROCS читается
из записанной метрики. STW-интервал включает остановку и возобновление P;
состояния G берутся из событий, общей заморозки нет. Счётчик mark учитывает
полностью записанные фазы. Метрики кучи прорежены, цель GC мягкая. Позы, декорации
и воспроизведение за 90 секунд объяснены в интерфейсе.

## Как поучаствовать

Архитектура нарезана так, чтобы три вида вклада было дёшево делать и дёшево ревьюить:

- **Сценарий** — один файл в `internal/scenarios/`, вызов `Register`, свой тест.
  Самый изолированный способ добавить то, что чему-то учит.
- **Язык** — один словарь в `web/src/i18n.ts`, причём вашу работу проверяет
  компилятор: пропущенная строка валит `tsc`, а не уезжает пустым лейблом.
- **Отчёт о достоверности** — «мир показывает X, а рантайм делает Y». Кода не
  требует и имеет наивысший приоритет.

Подробности — в [CONTRIBUTING.md](CONTRIBUTING.md), включая две ловушки, на
которых спотыкается каждый новый сценарий. Ещё: [кодекс поведения](CODE_OF_CONDUCT.md)
и [политика безопасности](SECURITY.md) — последнюю стоит прочитать до того, как
где-то поднимать бэкенд.

## Планы

**Дальше** — новые сценарии (отмена по контексту, воркер-пул с ограниченным
каналом, атомики против мьютекса); предсборка бинаря workload вместо `go run` на
каждый запрос; что-то, показывающее блокирующий syscall на Windows, где текущий
сценарий не работает.

**Возможно** — добавить измерения runtime, которые trace раскрывает напрямую,
включая загрузку CPU фоновыми mark-воркерами; вынести
конвейер трейс → Timeline в библиотеку.

**Не планируется** — публичный инстанс, записывающий трейсы вживую. Почему —
в [политике безопасности](SECURITY.md).

## Как это сделано

Разработано в паре с [Claude Code](https://claude.com/claude-code).
